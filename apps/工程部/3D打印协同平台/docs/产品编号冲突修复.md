# 产品编号冲突修复（2026-10-19）

两边分别新增产品时都使用递增数字编号，导致不同产品同时占用 658、659。旧处理页只能选择一边，整轮同步也因此被阻塞。

## 本次变更

新增“保留双方产品（原系统产品分配新编号）”选项，仅用于上次共同版本中不存在、双方都存在的产品。已有共同产品的编辑冲突仍逐项核对。

新平台产品保留编号，避免改变云端订单任务和独立产品附件的既有归属。原系统冲突产品获得高于两边现有产品编号的新数字编号；其业务 JSON 中的 productId 引用随之更新，名称及内嵌图片保留。实际新编号以当次双方目录为准，不能预先假定为 660、661。

处理选择绑定当前差异签名；资料改变后过期选择失效。云端事务保存重编号映射、双方当次批准的产品版本及回执。拆分后的两条产品还会分别携带 `_printlinkProductIdentity` 稳定身份字段；它随业务 JSON 写回 Windows，用于区分「仍在旧编号空间」与「已经完成 CAS 写回但确认丢失」。响应丢失、桥接重启和现场后续修改不会把云产品再次当成旧现场产品搬移。目标编号被现场其他产品占用时停止，不能覆盖该产品。

首次对账没有共同基线时，重试只继承已经明确批准的这两条产品版本；新增记录、库存和删除等其他差异仍须分别核对。映射保留的批准版本在 Windows 确认前保持不变，避免旧现场版本在多次重试中倒灌云端编辑。

独立模型/附件文件仍不属于业务 JSON 同步范围。本次不移动原系统磁盘上的附件；若原系统按产品编号保存独立附件，须在执行“保留双方”前核对并制定对应附件迁移。新平台既有附件编号不改变。

## 部署

本修复包只需更新云端项目中的以下文件：

- shared/business-sync.cjs
- production/business-sync.cjs
- cloud/public/business-sync.js

正式 RR-Portal 通过 PR 合并到 main 后，由 GitHub Actions 的差异部署流程更新 printlink 服务。部署前按现有流程备份生产数据；管理员检查部署结果、服务健康状态及页面新选项。不要另外并行执行手动 Compose 部署，不要删除数据卷或覆盖现场配置、SQLite 数据库。

已安装全业务双向同步适配器的 Windows 桥接无需为本次新增选择重新安装；写回继续使用原有 CAS 和业务快照接口。旧适配器的 core.project/core.apply 保留产品行未知字段；旧产品编辑页原地 Object.assign 产品行，saveAll 全量提交，服务器 saveData 整体 JSON 序列化，均保留稳定身份。仓库参照为 archived/3d-print-management/index.html 的 saveProduct/saveAll 和 archived/3d-print-management/server.js 的 saveData。若现场曾自行更改这些行为，应先在隔离副本验证身份字段能往返，不能假定任意外部工具都会保留字段。

若现场编辑了尚未标记的旧产品、外部工具剥离了身份字段，或已有旧版 from/to-only 映射，系统无法确认当前编号空间，会暂停写入并在处理页显示「产品编号归属」。展开两边说明后：选择「使用新平台值」表示现场已经使用新平台编号，应保留当前编号；选择「使用原 3d-server 值」表示现场仍使用旧编号，应执行旧现场产品重编号。该选择只确认编号归属，不批准其他业务差异；资料再改变后选择失效。确认旧编号空间时目标已占用仍会拒绝。不得按产品名称猜测，也不得删映射表、身份字段或共同基线来绕过检查。已有同名身份字段但格式不符时保留原字段并停止拆分。若以后重装适配器，可使用更新后的 shared/business-sync.cjs。

## 现场核对边界

本修复上线只提供新的处理能力，不等于已经选择了任何生产冲突。管理员应保留双方备份，逐项核对产品身份、编号与附件归属，再决定是否使用「保留双方」。库存余额及删除标记须分别依据当时可验证的业务记录处理；本说明不代表用户已经授权某一方库存或删除选择。

保存选择后等待桥接完成，检查双方产品与图片、业务引用、库存和记录，并确认 Windows 成功时间更新。发生新差异或编号归属确认时，重新核对当前内容，不沿用旧截图数值。本地隔离测试通过不代表生产部署或现场冲突处理完成。
