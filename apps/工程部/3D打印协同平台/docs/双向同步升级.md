# 全业务双向同步升级

本功能需要云端、Windows 桥接、原 3d-server 三处一起更新。只部署云端不会开启双向同步。默认关闭，沿用原有单向记录同步。

## 范围与规则

- 同步每日生产记录（包括数量、材料、报价、客户、时间、删除标记）、产品库、材料、排期、杂费、维修、材料库存和入库记录；图片为业务 JSON 内嵌图片时同步。同步机器数量、电费、人工、损耗及利润等业务设置。
- 订单、账号、权限、采集令牌、打印机连接配置仍各自管理。独立保存的 3D 模型/附件文件不在此 JSON 同步范围内，不能仅复制文件描述信息代替实际文件迁移。
- 以稳定记录 ID 关联，不用产品名称猜测。同一实体两边新增但 ID 重复时要求核对。每 30 秒对账一次；双方无变化时只上传摘要，变化时交换业务快照（请求上限 128MB，含共同基线与本地资料）。反向代理请求上限至少 128MB，超时至少 120 秒。
- 上次一致数据作为共同基线：只有一边修改的字段自动传播，不同字段分别修改可合并，同一字段同时修改、删除与修改相撞时保留双方值并暂停整轮写入。
- 首次没有共同基线，两边不同值及单边独有记录都需要管理员选择，不能假定 51 条或 49 条哪边正确。核对 10 月 10 日机台、时间、数量、报价等后再选择。不要清空任何一边重新导入。
- 库存只复制确认后的余额，不重放“新增记录→扣库存”。启用后，云端停止原桥接记录自动扣料；打印机自动记录产生的扣料由原系统负责。任意一边手工调整库存/入库后，将其结果同步。两边同时修改同种材料余额，包括恰好改成同一个数，都要求核对；若两个独立领料需要累计，应先在一边登记正确余额，再选择该值。
- 完成对账后每日记录显示「共享库存」，表示库存由双向同步管理，不代表缺少料重的每条记录都已经扣料。未匹配材料/料重的记录仍须补充并核实实际库存。
- 原质检入账接口在双向模式下拒绝执行，避免再扣一次。订单仍由新平台生产任务推进。同步业务资料本身不会触发订单交付，也不会控制打印机。
- 冲突处理页：云端顶部「双向同步」或 `/business-sync`，仅管理员有权查看/处理。可逐项保存选择；全轮冲突都处理后才应用。数据再变化时，过期选择失效，重新核对。

## 上线前

1. 约定首次对账窗口，暂停两边人工编辑；暂停 Windows 桥接。停止原 3d-server 后备份整个目录（至少 server.js、config.json、data.json 和附件），备份云端数据卷及 Windows 桥接 data 目录。备份中含凭据，不要发微信群。
2. 只允许一台 Windows 桥接进程负责全业务双向同步。云端会绑定首个桥接实例 ID，另一数据目录启动的实例会被拒绝；升级必须保留原 data 目录。异常退出遗留 data/collector/.platform-lock 时，先确认桥接进程已全部退出，再清理该锁目录。原系统旧主从/对等同步必须关闭，角色不能是 slave；否则安装器/接口拒绝启用。保留原采集机台映射和原登录凭据。
3. Windows 桥接需要 Node.js 24+；原 server.js 运行环境应支持 structuredClone（Node.js 18+）。安装器会检查当前原服务器接口特征，不匹配时停止，不自行覆盖整个原服务。

## 更新云端

合并本次变更，按现有部署方式重建应用。设置 `BUSINESS_SYNC_STATION` 为 `runtime/stations.json` 中清溪采集站的准确 `id`，不是站点显示名称或令牌。本应用独立 compose.yaml 已透传该环境变量；其他部署方式也需把它传给 cloud 与 production 两个子服务。

这是该站点对全部业务资料的读写授权。其他采集站仍只能使用其原设备权限。环境变量未设置时不开启新同步；设置后旧单向 `/records` 上报明确拒绝，直到 Windows 完成升级。

## 更新 Windows

1. 停止桥接和原 3d-server。把更新包内 collector、shared、legacy、ops 目录合并复制到桥接目录（例如 `D:\PrintLinkBridge`）。保留原配置、data、bindings 文件，不用示例配置替换凭据。
2. 在桥接目录运行（将路径换成原服务器真实目录）：

   ```bat
   node legacy\install-business-sync.mjs "D:\3d-server"
   ```

   安装器备份原 server.js 为 `server.js.before-business-sync`，加入经过原 Basic Auth 验证、仅本机可调用的 `/api/business-sync` 接口，并复制两个适配模块。重复运行不会重复插入接口，不改业务资料或配置。
3. 原 3d-server 的 `config.json` 顶层加 `"businessSync": true`，保证旧 `sync.enabled` 为 false 且不是 slave。桥接正在使用的 JSON 配置顶层也加 `"businessSync": true`。保持 `mode: "bridge"`，`legacy.url` 为同一 Windows 电脑回环地址，如 `http://127.0.0.1:3000`；保留其账号密码与 machineMap。
4. 先启动原 3d-server，再用原有启动方式启动桥接（保留 `--bridge`）。现场控制台 `http://127.0.0.1:3103` 将显示「全业务双向同步」及成功轮数，不再把轮数显示成记录条数。
5. 新平台 `/business-sync` 核对并选择首次差异，尤其材料余额和单边多出的记录。选择后等下一轮，确认 Windows 控制台显示成功时间，再恢复日常编辑。

## 验收

- 云端改一条产品备注，在原系统刷新后核对；原系统改另一条每日记录的数量/报价，云端刷新后核对。
- 同一条记录同一字段两边同时改成不同值，应出现冲突且不静默覆盖；选择一方后两边一致。删除与修改冲突也需处理。
- 记录某材料余额，完成一次自动打印记录，确认仅扣一次；重启桥接、反复刷新与断网恢复后余额不能再次减少。
- 对账 10 月 10 日总条数之外，还要逐条核对 ID/机台/时间/数量/材料/报价。总条数一样不能代替字段一致。
- 两边离线编辑同一材料后应出现库存冲突，不能自动相加或按时间覆盖。

## 故障与恢复

Windows 以 SQLite 保存共同基线，只有原系统写回并通过磁盘校验后才推进。云端事务保存处理回执，丢失响应后同一批重试不会重扣。原系统数据在读取后变化，写回被拒绝，下一轮重新对账；磁盘写入失败或内存与文件不一致时停止确认，需要检查磁盘/权限，必要时重启原服务后重试。

云端 business_sync_backups 表保留最近 5 次写入前的完整快照，原系统继续使用自身写入备份；这不替代首次升级前的独立备份。Windows data/collector/outbox.sqlite 内的 business_sync_base 不能单独随意删除；丢失后将重新进行首次差异核对。

遇到问题先停止 Windows 桥接，保留两边数据库与错误信息，核对后恢复。已经启动过双向对账后，云端会记住该状态，取消环境变量也不会重新对历史源记录自动扣料；回退单向模式须先人工核对库存及扣料基线，不能只切开关重跑历史记录。

本次只提供代码与隔离测试，尚未在用户的 Windows 真机及云端执行首次对账，也未改变现有生产数据。
