# 物料追踪历史保留

## 行为

- 默认累计追踪现存排期和后续上传版本。相同客户、订单号、完整货号、物料 ID（生产件为模具/部件键）按归档版本顺序采用最新需求（不以可补填的上传日期覆盖版本顺序），不跨周累加；同一版本中的重复行仍按原规则求和。
- 新排期缺席的历史订单不自动视为取消或删除；同一版本内该订单、客户和完整货号的数量合计明确改为 0 时不再计算其所有需求，包括已移出当前 BOM 的历史物料。无订单号的行无法可靠跨版本匹配，只计入最新版本，旧行仍可在历史筛选中查看。
- 手动送完按上述身份保留已确认数量；追加需求、新订单、新物料不自动完成。手动确认与真实入出库取覆盖量而非相加，不生成库存流水。
- 下拉选择历史版本可查看当时的需求及物料资料。实际采购/入出库仍使用当前账面记录并沿用 FIFO 分配，不是历史库存快照。

## 持久化与升级边界

`material_tracking_history` 保存排期原文、当时 BOM、确认标记。首次启动归档数据库中仍存在的所有排期；上传事务先归档旧版，再覆盖排期，再归档新版。历史表独立保留，不随排期覆盖而删除。当前累计视图的最新排期仍使用现有物料库，旧版本使用归档 BOM。

首次升级没有过去的 BOM 快照，只能用升级时物料库初始化。旧手动确认仅在保存的排期哈希匹配时迁入；已覆盖且没有原文/备份的旧排期及失效确认不能自动恢复，禁止猜测完成状态。

接口：`GET /api/material-alerts/history`、`GET /api/material-alerts?revisionId=...`；无 revisionId 为累计视图。不存在的版本返回 404。

## 验证

`MaterialCompletionIntegrationTests` 使用 `SUPPLIER_SYNC_TEST_CONNECTION` 指向隔离 PostgreSQL；每项测试建立独立 schema，结束后清理。覆盖换周、同周覆盖及回退、追加数量、旧订单保留、新身份隔离、BOM 变化、重复行、零需求、缺失订单号、空排期和失效确认。不要将测试连接指向业务库。
