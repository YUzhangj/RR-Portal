## 1. 技术栈（已锁定）

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **.NET 8 (ASP.NET Core Web API)** | 与 SQL Server 最原生；T-SQL 算法/建表脚本零翻译；重事务/审核过账最稳 |
| ORM | **EF Core**（CRUD）+ **Dapper**（库存/对账/报表大查询） | 标准 CRUD 用 EF Core；UNION 符号法等手写大查询用 Dapper |
| 数据库 | **SQL Server** | `rebuild_schema.sql` / `rebuild_relations.sql` 直接可用 |
| 前端 | **React + TypeScript + Ant Design**（ProTable/ProForm） | 重表格/重表单/重中文录入体验最好 |
| 认证 | JWT + **bcrypt** + `userbqrpower` 9位权限 → Authorization Policy | 落实安全基线 |
| 部署 | 单厂内网：Kestrel/IIS + SQL Server（可选 Docker） | 单租户，架构最简 |

**为什么 .NET 而非 Java**：SQL Server 已锁定，.NET 在驱动、迁移、T-SQL 复用、调试上更顺；算法文档全是 T-SQL，.NET 复用率最高。

```
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│  SQL Server  146表(rebuild_schema)+233外键(relations)     │
│  + 结存快照表 + 单号流水表 + 系统配置表(3张新增优化/加固表)   │
└─────────────────────────────────────────────────────────┘
```

**关键设计决定**
1. **4 个横切引擎先建**（P0），作为 12 模块的公共底座，抽成独立可测试组件，而非散落各模块。
2. **库存汇总**用文档 UNION 符号法（Dapper），并**新增结存快照表按月滚存**，解决"数据大了慢"。
3. **安全基线**：bcrypt、JWT、连接串配置加密、无后门、无日期删库逻辑、不存明文错误密码。

## 5. 数据层落地方案

### 5.1 建库三步
1. `rebuild_schema.sql` → 146 表（ID自增主键，ntext→nvarchar(max)，image→varbinary(max)）
2. `rebuild_relations.sql` → 主表唯一键 + 233 外键（25 主从 + 208 查找）
3. 新增 3 张重建专用表（不在原 146 内）：
   - **结存快照表**（款号,颜色,尺码,仓库,年月,期初,本期入,本期出,结存）— 库存滚存优化
   - **单号流水表**（单据类型,日期,当日流水）— 单号生成并发安全
   - **系统配置表**（键,值,加密标志）— 替代硬编码连接串/参数

### 5.2 表按角色分三类
| 类别 | 例子 | 代码处理 |
|---|---|---|
| 主数据表 | 客户资料、款号总表、物料资料、人事档案 | EF Core 实体 + CRUD，做下拉数据源 |
| 单据三层表 | 采购入仓单+明细+总单 | 统一"单据基类"：共有 `单号/审核/审核人/审核日期` |
| 汇总/报表 | 库存、应收应付、计件汇总 | Dapper 只读 SQL，不建实体 |

## 6. 四个横切引擎（P0 先建）

**① 单据三层 + 单号生成器**
- `DocumentBase { 单号, 审核, 审核人, 审核日期 }`；`明细单.单号 = 单.单号` 主从串联（EF Core 导航属性）。
- 单号 = 前缀 + yyyyMMdd + 当日流水(补零)，用"单号流水表"+行锁保证并发不撞号（修掉原 `max+1` 并发隐患）。

**② 审核过账引擎**
```
审核(单号): 校验 userbqrpower.审核位=1 → 事务内 update 单 set 审核='1',审核人,审核日期
           → 写 c操作记录 → 库存/账目无需写余额(汇总只认审核='1',算法1/5自动反映)
反审核(单号): 先校验未被下游引用 → 审核'1'→'0'
```

**③ 库存汇总引擎（Dapper）**
- 实时层：算法1 的 UNION ALL 符号法（入 +数量 / 出 −数量），仅 `审核='1'`，按 款号×颜色×尺码×仓库 group sum。
- 快照层：月末滚入结存快照表；查询 = 最近快照(期初) + 快照后至今的实时增量 → 解决全表汇总慢。

**④ 权限矩阵 + 审计**
- `userbqrpower`：用户 × 菜单 × 9位（打开/保存/删除/打印/单价/金额/审核/反审核/功能）→ ASP.NET Authorization Policy。
- "单价/金额"两位单独控 = 前端按位隐藏价格列（成本保密，照搬原设计）。
- `c操作记录`：增删改审核 关键动作各写一条审计。

## 8. 安全基线（逐条兑现）

| 原软件的坑 | 重建做法 |
|---|---|
| 万能密码后门 `zsbqr.com!#(` | 彻底无后门，登录只走 bcrypt 比对 |
| MD5 弱哈希 + 存明文错密 | bcrypt 加盐；错误次数只存计数，不存明文密码 |
| 硬编码连接串/密码 | 进系统配置表/环境变量，加密存储 |
| 任何日期"删库"逻辑 | 不存在，代码审查兜底 |
| 连错5次锁定 | 保留（好设计） |

## 9. Django → .NET 移植方案（M8 库存/仓储，落 P5）

M8 是库存汇总引擎③所在地，你已有 Django 实现（中等体量，一个完整模块），等于这块有现成"活规格"与验证基准。

### 9.1 移植映射
| Django 构件 | .NET 8 对应物 |
|---|---|
| models.py | EF Core 实体（DB-First 反向生成，表已由 rebuild_schema 建好，不让 EF 重新建表）|
| ORM 聚合查询 | 库存汇总改写为 Dapper UNION 符号法（算法1）；普通 CRUD 用 EF Core LINQ |
| views/DRF serializer | ASP.NET Controller + DTO + FluentValidation |
| 业务逻辑(过账/盘点) | 复用审核过账引擎② + 盘点盈亏(算法7) |
| Django Admin | React + Ant Design ProTable 前端重建（不移植 Admin）|
| Django 权限 | 并入 `userbqrpower` 9位权限矩阵（引擎④）|
| 单元测试 | xUnit 重写；Django 结果做"黄金基准"对拍 |

### 9.2 对拍验证（关键安全网）
库存算钱必须零误差：Django 旧库与 .NET 新库用同一测试数据，跑同样库存查询，逐行 diff，**完全一致才算移植成功**——把"能否100%合并"从口头承诺变成可验证测试。

### 9.3 数据迁移
若 Django 已有真实库存数据：写一次性迁移脚本，按字段映射导入新库 146 表结构；迁移后用 9.2 对拍验证总库存对得上。单厂内网中等体量，风险可控。
