# P4 M7 发外加工（派工 → 回收 → 对数）设计

> 阶段：P4 生产侧 M7（M6 已完成并合并 master）。本设计只覆盖 **派工 + 回收 + 对数**；加工费付款/扣款/结款随收付款延后到 P6。

## 1. 目标与业务闭环

打通服装厂**厂外协作闭环**：

1. **发外派工**：把裁好的片/半成品按 加工厂×款×加工项目×色×码 发给外部加工厂做某工序（如车缝/印花/绣花），记发出数量与加工单价。
2. **发外回收**：加工厂交回成品，按发外单逐明细记回收数量，自动算欠数（发外数量 − 累计回收）。
3. **发外对数**：按 加工厂×发外单×款×加工项目 核对 发外数量 / 回收数量 / 相差 / 金额——这是 P6 应付对账与加工费结算的源头。

可演示命题：发外 100 件 → 回收 95 件 → 对数显示 相差 5 件、金额 = 回收数量 × 单价。

## 2. 关键设计决策（brainstorming 已定）

1. **范围**：派工 + 回收 + 对数。付款/扣款/结款延后 P6（与收付款、应付对账算法5 一起做，避免口径割裂）。
2. **单价来源**：`发外加工项目`（全局费率主数据，加工项目→单价）。派工选加工项目时带出默认单价（可改）；服务端按加工项目取价、金额 = 数量 × 单价，**不信任前端传的单价**（与 M6 计件取数同构）。
3. **单据结构 + 对数落地（方案 A）**：派工/回收都用 **头 + 明细 两层**（照搬 M6 头+明细、P3 物料单据），跳过遗留的「总单」颜色/尺码矩阵层；**对数用 Dapper GROUP BY 实时聚合、只读**（不落地写 `发外加工对数表`），与 M6 计件汇总同构。

## 3. 涉及表的真实结构（以 `db/01_rebuild_schema.sql` 为准）

> 仅列出本期实际读写的列；遗留表有更多列（含矩阵「组」列、扣款、结款等），本期不写。

- **发外加工项目**（费率主数据）：`ID bigint`, `加工项目 nvarchar`, `单价 decimal`, `备注 nvarchar`。
- **发外加工单**（派工·单头）：`ID int`, `单号 nvarchar(20)`, `日期`, `加工厂编号`, `加工厂名称`, `付款方式`, `仓库`, `数量 decimal`, `金额 decimal`, `操作员`, `审核 nvarchar`, `备注`, `计算帐款`。**无 审核人/审核日期 列（05 脚本补）**。
- **发外加工明细单**（派工·明细）：`ID int`, `单号 nvarchar(20)`, `日期`, `加工厂编号/名称`, `仓库`, `生产单号`, `款号`, `款式`, `床号`, `加工项目`, `色号`, `颜色`, `尺码`, `数量 decimal`, `单价 decimal`, `金额 decimal`, `审核`, `备注`。按「单号」串联单头（无主从 FK，逻辑串联，与裁床同构）。
- **发外回收单**（回收·单头）：`ID int`, `单号 nvarchar(20)`, `发外单号 nvarchar(20)`, `日期`, `加工厂编号/名称`, `付款方式`, `仓库`, `发外数量 decimal`, `回收数量 decimal`, `相差数量 decimal`, `金额 decimal`, `操作员`, `审核`, `备注`。**无 审核人/审核日期（05 脚本补）**。
- **发外回收明细单**（回收·明细）：`ID int`, `单号`, `发外单号`, `日期`, `加工厂编号/名称`, `仓库`, `生产单号`, `款号`, `款式`, `床号`, `加工项目`, `色号`, `颜色`, `尺码`, `发外数量 decimal`, `数量 decimal`（=本次回收数量）, `欠数 decimal`, `单价 decimal`, `金额 decimal`, `审核`, `备注`。
- **发外加工对数表**（本期**不落地写**，仅作为字段口径参考）：加工厂×发外单×款×项目的 发外/回收/相差/结款数量、单价、金额、扣款、总金额、对数标志。

**已确认的横切现状**：
- `PostableDocuments` 白名单**已含** `发外加工单`、`发外回收单`（单号列 = `单号`）——**无需改白名单**。
- `生产制单` 仅有 `完成` 标志列，**无「发外完成数量」列** → 本期**不回写生产单**（与 M6 计件一致）。

## 5. 数据流与算法

**派工创建**（`发外加工单` 头 + N 条 `发外加工明细单`）：
- 每条明细按 `加工项目` 从 `发外加工项目` 查单价（服务端取数，不信前端）；`金额 = 数量 × 单价`。
- 单头 `数量 = Σ明细.数量`、`金额 = Σ明细.金额`、`审核='0'`。
- 单号 = `FW + yyyyMMdd + 3位流水`。事务：插单头 → 插明细；删除反序（先明细后单头，仅未审核可删）。

**回收创建**（`发外回收单` 头 + N 条 `发外回收明细单`，关联 `发外单号`）：
- 按发外单号拉派工明细作为基准（带出 发外数量、加工项目、款/色/码、单价）。
- 用户按明细录 `数量`（本次回收数量）；`欠数 = 发外数量 − 该发外明细的累计已回收（含本单）`。
- 单头 `发外数量 = Σ派工数量`、`回收数量 = Σ本单回收`、`相差数量 = 发外数量 − 累计回收`。
- 单号 = `FH + yyyyMMdd + 3位流水`。审核走引擎②。

**对数聚合**（只读，按 加工厂×发外单号×款号×加工项目）：
```
SELECT 加工厂编号,加工厂名称,发外单号,款号,款式,加工项目,
       SUM(发外数量) 发外数量,
       SUM(已审核回收数量) 回收数量,
       SUM(发外数量)-SUM(回收数量) 相差数量,
       单价, SUM(回收数量)*单价 金额        -- 金额以回收计（已交回才结）
FROM (派工明细 LEFT JOIN 回收明细 聚合) ...
GROUP BY 加工厂,发外单号,款,加工项目
```
口径：发外数量取派工（审核'1'）；回收数量取回收明细（审核'1'）；金额按回收数量计（已交回部分才结算）。单价取该发外单该项目的派工单价。

## 6. 成本保密

- 派工明细、回收明细的 `单价`/`金额`，发外对数的 `单价`/`金额`：无「单价」权限时后端置 null（前端显示 `***`）。
- `发外加工项目` 的 `单价`：走 P1 `[PriceField]` 机制。

## 10. 明确延后（已记录）

1. **加工费付款/扣款/结款**（`发外加工付款单`/明细、对数表的 扣款/结款数量/对数确认）→ P6 随收付款、应付对账（算法5）。
2. **三层总单矩阵层**（`发外加工总单`/`发外回收总单` 的 颜色组/尺码组/数量组 打包列）——本期两层够用。
3. **`委托发外加工单`扎号条码逐扎发外**（算法11 条码线）——与 M6 条码扫描一致延后。
4. **回写生产单发外完成量**——生产制单无对应列，延后。
